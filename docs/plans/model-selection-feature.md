# План: Выбор модели в TemplateForm (дропдаун с поиском + shared-команда получения моделей)

> План для агента-исполнителя. Ветка: `ModelSelectionFeature` (от `main`).
> Цель: в форме шаблона на вкладке API поле «модель» становится дропдауном
> с поиском и скроллом; список моделей тянется с сервера провайдера по
> вставленному API-ключу (OpenAI-совместимый `GET {baseUrl}/models`);
> команда получения моделей живёт в `shared` и переиспользуется на других
> страницах (FastCheck и др.); без ключа модель выбрать нельзя
> (superRefine + подсветка поля ключа + короткий тост, ru/en через i18n).

## 1. Что делаем (сводка)

1. **Search-надстройка в shared**: утилиты FTS-матчинга
   (`buildFtsMatchQuery` + константы: минимальная длина префикса,
   highlight-маркеры, лимиты) переезжают из `search-repository.ts` в
   `src/shared/lib/search/`. Репозиторий импортирует их оттуда. Поведение
   поиска чатов не меняется — это чистый рефакторинг-вынос, дубликатов нет.
   Фильтр по моделям (case-insensitive подстрока) в эту либу НЕ входит —
   он нужен только в одном месте и живёт внутри `ModelSelect`.
2. **Shared-команда получения моделей**: `src/shared/lib/ai/models.ts` —
   чистая функция `fetchAvailableModels({ baseUrl, apiKey, signal })`,
   `GET {baseUrl}/models` с `Authorization: Bearer`, парсинг
   OpenAI-совместимого ответа (`data[].id`), dedup + sort, возвращает
   `string[]`. Никаких зависимостей от `features` и от UI — вызывается
   откуда угодно (сейчас TemplateForm, потом FastCheck).
3. **Стор-кэш моделей**: `src/shared/lib/ai/models-store.ts` — zustand-стор
   рядом с командой. In-memory на сессию, ключ кэша `provider|apiKey`
   (provider берём из формы шаблона). Статусы `idle | loading | ready |
   error`. In-flight дедупликация (повторный запрос по тому же ключу не
   создаёт второй fetch), AbortController: смена ключа абортит старый
   запрос, чтобы ответ от старого ключа не перезаписал состояние.
4. **Компонент `ModelSelect`**: `src/shared/components/ModelSelect/` —
   переиспользуемый. Сверху поле поиска, снизу скролл-список (`FlatList`,
   виртуализация обязательна — OpenRouter отдаёт ~300 моделей). Фильтр —
   case-insensitive подстрока в любом месте id. Выбранная модель
   подсвечивается и записывается в форму через `onChange`. Если список
   моделей не получен (ошибка сети/401/пустой ответ) — компонент молча
   рендерит обычный `TextInput` ввода имени модели: ничего не «падает»,
   никаких тостов/retry, юзер вводит имя вручную.
5. **Интеграция в TemplateForm**:
   - авто-запрос списка при вводе ключа: debounce 700ms после остановки
     ввода, длина ключа ≥ 20 символов; повторная вставка того же ключа —
     из кэша стора, запроса нет;
   - смена ключа сбрасывает выбранную модель (модель может не существовать
     у нового ключа);
   - superRefine в `apiTemplateFormSchema`: попытка выбрать/оставить модель
     без ключа → ошибка на поле `apiKey` (подсветка) + короткий тост
     «Сначала введите ключ» (ru/en), тост быстро исчезает (существующий
     паттерн `showToast`).

## 2. Задачи

### Задача 1. Вынос FTS-утилит в `src/shared/lib/search/`

Создать `src/shared/lib/search/` с файлом утилит и файлом констант/типов
(типы и константы — в отдельных файлах, не рядом с логикой, см. принципы
в п.3). Перенести туда `buildFtsMatchQuery` и поисковые константы из
`src/lib/db/search-repository.ts` (минимальная длина префикса, лимиты,
highlight-маркеры — всё, что относится к матчингу). `search-repository.ts`
импортирует утилиты из нового места; логика и результаты поиска чатов
не меняются ни на символ. Проверить, что других копий этой логики в
проекте нет (grep по `MATCH`, `fts`) — если есть, свести на общий импорт.

Ссылки: `src/lib/db/search-repository.ts`, `docs/features/chats-search.md`
(раздел про матчинг), `src/features/chats/model/use-chat-search.ts`.

### Задача 2. Типы и конфиг команды моделей

Создать `src/shared/lib/ai/models.types.ts`: типы параметров команды
(`baseUrl`, `apiKey`, `signal`), тип элемента ответа провайдера и тип
результата (`string[]`). Константы (таймаут запроса, минимальная длина
ключа для авто-запроса = 20, debounce = 700ms) — в
`src/shared/lib/ai/models.config.ts`. Никаких значений-«магий» внутри
логики: всё читается из конфига.

Ссылки: `src/lib/ai/embeddings/embeddings.types.ts` (образец вынесения
типов), `src/types/api-template.ts` (откуда берутся `baseUrl`/`provider`
формы).

### Задача 3. Команда `fetchAvailableModels`

`src/shared/lib/ai/models.ts`: функция принимает `{ baseUrl, apiKey,
signal }`, делает нативный `fetch` `GET {baseUrl}/models` с заголовком
`Authorization: Bearer <apiKey>` (тот же паттерн, что
`openai-compat-client.ts` — нативный запрос с устройства, без бекенда,
ключ не логируется и никуда не пишется). Парсит OpenAI-совместимый ответ
(`data[].id`), нормализует: trim, dedup, сортировка по алфавиту. Ошибки
классифицирует в понятный наружу результат: сеть / 401-403 (неверный
ключ) / прочее — без выброса необработанных исключений наверх. Логика —
только в этом файле, типы из `models.types.ts`, константы из
`models.config.ts`. Комментарий оставить только на неочевидном: почему
нормализация dedup+sort (разные провайдеры отдают дубли и разный порядок).

Ссылки: `src/lib/ai/openai-compat-client.ts` (стиль клиента, обработка
не-2xx), `src/lib/ai/embeddings/embeddings-client.ts`.

### Задача 4. Стор-кэш моделей

`src/shared/lib/ai/models-store.ts` + `models-store.types.ts` (типы —
отдельным файлом). Zustand-стор по образцу `templates-store.ts`:

- состояние: Map записей, ключ записи — `provider|apiKey`; запись:
  `status` (`idle | loading | ready | error`), `models: string[]`;
- экшен «обеспечить список» (`ensureModels`): если запись `ready` —
  вернуть из кэша, запроса нет (требование кэширования при повторной
  вставке того же ключа); если `loading` — не запускать второй запрос
  (in-flight дедупликация); иначе запустить `fetchAvailableModels`;
- экшен «сбросить по ключу»: при смене ключа в форме старый in-flight
  запрос абортится через `AbortController`, чтобы ответ от старого ключа
  не перезаписал состояние новой записи;
- стор ничего не персистит: рестарт приложения → список запрашивается
  заново (in-memory на сессию — принятое решение).

Ссылки: `src/features/api-templates/model/templates-store.ts` (паттерн
стора), `src/features/chats/model/chats-store.types.ts` (типы рядом).

### Задача 5. Компонент `ModelSelect`

`src/shared/components/ModelSelect/` (плюс подпапки по образцу
`TemplateForm`). Переиспользуемый, props: `baseUrl`, `provider`,
`apiKey`, `value`, `onChange`, `disabled`. Флоу:

- подписан на стор моделей по ключу `provider|apiKey`;
- если статус `ready` и список непустой: рендер — поле поиска сверху
  (UX как поиск в `ChatSidebar`: локальный стейт, мгновенная фильтрация),
  под ним скролл-список `FlatList` (виртуализация обязательна);
  фильтр — case-insensitive подстрока в любом месте id (реализуется
  локально в компоненте, в shared search-либу НЕ выносится — решение
  принято); выбранная модель подсвечивается; тап по элементу вызывает
  `onChange(name)` и закрывает список; повторный тап по полю снова
  открывает список;
- если статус `error` ИЛИ список пустой: компонент рендерит обычный
  `TextInput` ввода имени модели — молча, без тостов, без retry, без
  сообщений об ошибке (принятое решение: возможно, у провайдера просто
  нет `/models`; юзер вводит имя вручную);
- если статус `loading`: поле модели показывает состояние загрузки
  (спиннер/плейсхолдер), выбор пока недоступен;
- если `apiKey` пуст: дропдаун не открывается (выбор блокируется —
  финальная защита на уровне UI, основная — superRefine из задачи 6).

Типы пропсов — в отдельном файле компонента (`ModelSelect.types.ts`).
i18n-строки (плейсхолдер поиска, «модель не найдена» в пустом
отфильтрованном списке) — через `useTranslation`, ключи в `en.json`/`ru.json`.

Ссылки: `ChatSidebar.tsx` (паттерн поискового поля), `TemplateForm.tsx`
(паттерн поля формы и ошибок), `src/shared/components/ui/` (стиль
базовых компонентов).

### Задача 6. Валидация superRefine + тост

В `src/schemas/api-template.ts` добавить `superRefine`-правило: если
`model` заполнен/выбирается, а `apiKey` пуст — ошибка вешается на поле
`apiKey` (не на модель: ошибка указывает на причину). В
`useTemplateForm.ts` в обработчике невалидной формы — короткий тост
«Сначала введите ключ» через существующий `showToast` (паттерн уже есть
в этом файле — `apiTab.invalidForm`), тексты добавить в `en.json`/`ru.json`
в секцию `apiTab`. Тост короткоживущий (существующее поведение Toast).

Ссылки: `src/schemas/api-template.ts`, `useTemplateForm.ts` (строки с
`showToast`), `src/shared/components/ui/Toast/`.

### Задача 7. Интеграция в TemplateForm

В `useTemplateForm.ts` / `TemplateForm.tsx`:

- подписка на ввод ключа: debounce 700ms (константа из `models.config.ts`),
  после остановки ввода, если длина ≥ 20 — вызов `ensureModels`;
  повторный ввод того же ключа повторного запроса не делает (кэш стора);
- при изменении ключа: сброс поля `model` в форме + вызов сброса
  in-flight запроса в сторе (задача 4);
- поле «модель» в форме заменяется на `ModelSelect` (задача 5), значение
  пишется в RHF через `setValue`/`onChange` по существующему паттерну
  полей формы;
- состояние ошибки загрузки моделей наружу не торчит: `ModelSelect` сам
  деградирует в инпут (задача 5), форма продолжает работать как раньше.

Ссылки: `TemplateForm.tsx`, `useTemplateForm.ts`, `docs/features/
api-templates-streaming-chat.md` (раздел про форму).

### Задача 8. Минимальные тесты (в конце, не перегружать)

Только самое ценное, без раздутия:

- утилита нормализации списка моделей (dedup + sort + парсинг `data[].id`)
  — чистая функция, простой unit-тест;
- superRefine-правило схемы: модель без ключа → ошибка на `apiKey`;
  модель с ключом → проходит;
- фильтр подстроки `ModelSelect` (case-insensitive, вхождение в середине
  id) — если он выделен в тестируемую чистую функцию; если нет — покрыть
  через тест схемы не нужно, пропустить.

Расположение — по существующему в проекте паттерну тестов (если папки
тестов нет — рядом с тестируемыми файлами, `*.test.ts`).

## 3. Принципы для исполнителя (обязательно)

- **FSD / типизация**: все типы — в отдельных файлах типов
  (`*.types.ts` / `src/types/`), все константы-конфиги — в отдельных
  конфиг-файлах (`*.config.ts`). В файлах логики и компонентов типов и
  магических констант не оставлять.
- **Переиспользуемость**: команда и стор моделей не должны импортировать
  ничего из `features/` и из `app/` — только `shared` и `lib`. Их будут
  вызывать с других страниц.
- **Комментарии**: только на действительно неочевидных местах (why, а не
  what). Не комментировать каждый шаг.
- **Дубликаты**: существующие паттерны взаимодействия (стор, форма, тост,
  i18n, поиск) — переиспользовать, не копировать. FTS-утилиты — один
  экземпляр в `shared/lib/search`.
- **Документацию не писать и не просить** — она будет делаться после
  полного рефакторинга отдельным шагом.
- **Тесты — в конце, минимальные** (задача 8), агента не перегружать.
