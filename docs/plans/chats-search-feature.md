# План: Поиск чатов (FTS5 по ключевым словам + embedding-задел)

> План для агента-исполнителя. Ветка: `ChatsSearchFeature` (от `main`).
> Цель: рабочий поиск чатов по названию (и по контексту — как только появится
> отправка сообщений), плюс готовая инфраструктура embedding-поиска, которая
> заработает сразу после подключения API и выбора модели.

## 1. Что делаем (сводка)

1. **Миграция v3**: в `chats` добавляются колонки `context` (денормализованный
   текст всех сообщений чата), `title_embedding`, `context_embedding`
   (эмбединги, пока NULL). Создается FTS5-таблица `chats_fts` (title + context)
   с триггерами синхронизации.
2. **Embedding-обёртка** в `src/lib/ai/`: провайдер-адаптер по образу
   OpenAI-совместимого API (OpenRouter). Только интерфейс и реализация клиента —
   **без подключения к приложению**: API-ключ и модель будут выбраны позже.
3. **Репозиторий поиска**: keyword-поиск через FTS5 (`MATCH`), выборка
   сохраненных эмбедингов чатов для сравнения.
4. **Стор поиска** (zustand, по паттерну `chats-store`): поисковая строка —
   временное состояние в памяти (как драфты), без записи в БД; результаты
   двух этапов поиска и их мерж.
5. **UI в сайдбаре**: при непустом запросе — плоский список найденных чатов
   (без группировки по датам) с подсветкой совпадений в названии; при пустом —
   обычный сгруппированный список как сейчас.

**Что работает сразу после реализации:** поиск по названию чата.
**Что заработает автоматически позже:** keyword-поиск по `context` (колонка
заполнится, когда появится отправка сообщений) и embedding-поиск (когда
подключат API, выберут модель и начнут генерировать эмбединги).

## 2. Принятые архитектурные решения

1. **Context — денормализованная колонка** в `chats`, а не сборка из `messages`
   на лету. При добавлении каждого сообщения (в будущем) текст аппендится в
   `context`. Поиск читает одну колонку — быстро и просто. Дублирование с
   `messages` осознанное: `messages` — источник истины для отображения истории,
   `context` — поисковый индекс.
2. **Keyword-поиск — SQLite FTS5** (доступен в expo-sqlite). Виртуальная
   таблица + триггеры — синхронизация индекса автоматическая, без ручных
   вызовов из репозитория.
3. **Два независимых дебаунса**: keyword-поиск выполняется мгновенно на каждый
   ввод (локальный FTS, дешево); embedding-поиск — с дебаунсом ~400мс после
   остановки печати + отмена устаревших запросов (AbortController). Это экономит
   API-вызовы, когда они появятся.
4. **Similarity threshold = 0.75** (cosine similarity), константой в конфиге
   embedding-слоя.
5. **Результаты — плоский список** без группировки по датам; показываем
   название с подсветкой совпадений. Сниппеты из context — позже, не в этой
   итерации.
6. **Мерж результатов**: dedupe по id чата; чат, найденный обоими этапами,
   остается одним элементом (приоритет у keyword-результата для подсветки).

### Задача 1. Миграция v3: колонки + FTS5

Файлы: `src/lib/db/db.config.ts`, `src/lib/db/migrations.ts`, `src/types/chat.ts`.

Флоу:

1. Поднять `DB_SCHEMA_VERSION` до 3 в `db.config.ts`.
2. В `migrations.ts` добавить блок `if (current < 3)` по образцу v2:
   - `ALTER TABLE chats ADD COLUMN context TEXT NOT NULL DEFAULT ''`;
   - `ALTER TABLE chats ADD COLUMN title_embedding TEXT` (NULL = эмбединг
     еще не сгенерирован);
   - `ALTER TABLE chats ADD COLUMN context_embedding TEXT` (NULL — задел
     на будущее);
   - создать виртуальную таблицу `chats_fts` через
     `CREATE VIRTUAL TABLE ... USING fts5(chat_id UNINDEXED, title, context,
     content='chats', content_rowid=...)` — external-content вариант, чтобы
     не дублировать текст. Внимание: у `chats` нет rowid-совместимого
     INTEGER PRIMARY KEY, поэтому если external-content не ложится cleanly —
     допустим вариант обычной FTS5-таблицы, где `chat_id` хранится UNINDEXED-
     колонкой, а триггеры поддерживают её актуальность. Решение принимает
     исполнитель по факту проверки на устройстве.
   - триггеры синхронизации: `chats_ai` (AFTER INSERT), `chats_ad`
     (AFTER DELETE), `chats_au` (AFTER UPDATE OF title, context) — вставка/
     удаление/обновление строки FTS-индекса при изменении `chats`.
   - для существующих БД после создания триггеров выполнить первичное
     наполнение индекса из текущих строк `chats` (INSERT INTO chats_fts
     SELECT ...). Идемпотентность: блок выполняется один раз по
     `user_version`, свежие БД проходят v1→v3 подряд — проверить, что
     порядок шагов корректен в обоих сценариях (как это сделано в v2).
3. Типы в `src/types/chat.ts`:
   - `ChatRow` дополнить полями `context`, `title_embedding`,
     `context_embedding` (snake_case, как в SQLite);
   - `ChatRecord` **не расширять** — UI-представление чата остается легким,
     context/эмбединги нужны только поисковому слою. Если поисковым функциям
     удобен отдельный рекорд — завести отдельный тип (например,
     `ChatSearchRow` / `ChatEmbeddingRecord`) в этом же файле типов.

### Задача 2. Репозиторий: поддержка новых колонок + поисковые функции

Файлы: `src/lib/db/chats-repository.ts`, новый `src/lib/db/search-repository.ts`,
`src/lib/db/index.ts`.

Флоу:

1. В `chats-repository.ts`: `createChat` при INSERT пишет `context: ''`
   (эмбединги — NULL, не указываем). `renameChat` остается без изменений —
   FTS-триггер подхватит обновление title сам. `mapRow` не трогаем (см. §3.1 —
   `ChatRecord` не расширяется).
2. Новый `search-repository.ts` (или функции внутри `chats-repository.ts`,
   если файл остается компактным — решить по образцу существующего размера):
   - `searchChatsByKeywords(query)` — SELECT из `chats`, JOIN с `chats_fts`
     по `MATCH`; запрос формируется из пользовательской строки безопасно
     (экранирование FTS-синтаксиса — кавычки, спецсимволы; параметризованный
     запрос). Возвращает: id чата, title, флаги/диапазоны совпадений в title
     (для подсветки — через FTS5-функцию `offsets()` или `highlight()`),
     релевантность (bm25). Сортировка: сначала совпадения в title, затем по
     релевантности. Поиск по `context` выполняется тем же запросом — сейчас
     колонка пустая и просто не даст совпадений, позже заработает сама.
   - `getChatEmbeddings()` — SELECT id, title_embedding, context_embedding
     из `chats`, отфильтровав NULL; возвращает список записей для сравнения
     (тип — из файла типов). Сейчас вернет пустой список — это корректное
     поведение до появления эмбедингов.
3. Реэкспортировать новые функции в `src/lib/db/index.ts` (по образцу
   существующих).

### Задача 3. Embedding-обёртка (без подключения)

Файлы: новый каталог `src/lib/ai/embeddings/` (структура по образцу
`src/shared/components/ui/ScrollIndicator/`: код, конфиг, типы, index).

Флоу:

1. Типы (`embeddings.types.ts`): интерфейс embedding-клиента
   (`embed(texts: string[]): Promise<number[][]>`), конфиг клиента
   (baseUrl, apiKey, model), тип вектора.
2. Конфиг (`embeddings.config.ts`): константы — `SIMILARITY_THRESHOLD = 0.75`,
   placeholder имени модели (например, OpenRouter-совместимый id, меняется
   позже одной строкой), дефолтный base URL OpenRouter
   (`https://openrouter.ai/api/v1` — согласуется с `src/lib/ai/providers.ts`).
3. Клиент (`embeddings-client.ts`): реализация OpenAI-совместимого
   `POST /embeddings` (body: model, input; разбор `data[].embedding`).
   Чистая функция поверх `fetch`, без side-effects, без чтения ключей из
   хранилищ — ключ передается аргументом (придет из SecureStore, когда
   появится подключение шаблонов).
4. Утилита cosine similarity — в `src/features/chats/lib/` (рядом с
   `group-chats-by-day.ts`, по его паттерну: чистая функция + при необходимости
   конфиг-файл). Нормализация векторов внутри функции.
5. **Ничего не подключать к UI/стору**: слой готов, вызовы появятся в задаче 5
   как вызовы клиента, но реально выполняться не будут, пока нет сохраненных
   эмбедингов и ключа. Проверка типа — компиляцией.

### Задача 4. Стор поиска + хук с дебаунсами

Файлы: `src/features/chats/model/search-store.ts`, `search-store.types.ts`,
`use-chat-search.ts`, реэкспорт в `src/features/chats/index.ts`.

Флоу:

1. Типы в `search-store.types.ts`: состояние поиска (query, результаты
   keyword/embedding/merged, флаг поиска, ошибка), тип результата
   (id чата, title, источник совпадения, диапазоны для подсветки, score).
   Тип результата — общий для двух этапов.
2. `search-store.ts` по паттерну `chats-store.ts` (чистые экшены, работа с
   репозиторием, никаких таймеров внутри стора):
   - состояние: `query`, `keywordResults`, `embeddingResults`, `isSearching`;
   - `searchByKeywords(query)` — синхронно зовет репозиторий (FTS — быстрый
     локальный запрос) и пишет `keywordResults`;
   - `searchByEmbeddings(query, signal)` — асинхронно: получить вектор
     запроса через embedding-клиент (задача 3), взять сохраненные эмбединги
     из репозитория, посчитать cosine similarity против `title_embedding` и
     `context_embedding`, отфильтровать по threshold 0.75, записать
     `embeddingResults`. Обертка в try/catch: ошибка сети/отсутствие ключа —
     тихо очищает embedding-результаты, не ломая keyword-поиск;
   - `clearSearch()` — сброс всего состояния поиска;
   - мерж двух списков — отдельная чистая функция в `src/features/chats/lib/`
     (dedupe по id, объединение источников совпадения, сортировка).
3. `use-chat-search.ts` — единственная точка входа UI (по образцу
   `use-chat-draft.ts`):
   - `onChangeText` → запись query в стор → **немедленный** keyword-поиск;
   - параллельно таймер-дебаунс ~400мс: по истечении — embedding-поиск;
     каждый новый ввод сбрасывает таймер и **прерывает** предыдущий
     embedding-запрос через AbortController (signal прокидывается в клиент);
   - пустая строка → `clearSearch()` + отмена таймера/запроса;
   - возвращает: query, merged-результаты, флаг активности поиска.
4. Реэкспорты в `src/features/chats/index.ts`.

### Задача 6. Проверка флоу (ручная, по чек-листу)

1. Создать несколько чатов с разными названиями → поиск по подстроке названия
   находит, подсветка корректна, регистр не важен.
2. Спецсимволы в запросе (`"`, `*`, скобки) не ломают FTS-запрос.
3. Пустой запрос → обычный сгруппированный список.
4. Запрос без совпадений → заглушка.
5. Быстрый набор текста: keyword-результаты обновляются на каждый символ;
   embedding-запрос (когда появится API) не уходит чаще, чем раз в ~400мс
   простоя; при переключении чата/закрытии сайдбара поиск сброшен.
6. Миграция: БД со старой версией (v2) поднимается на v3 без потери данных;
   свежая установка создает схему сразу v3.

## 4. Потоки данных (итоговые)

Ввод поискового запроса:

```
Печать в TextInput (ChatSidebar)
↓ onChangeText → useChatSearch
↓ query → search-store (память, без БД — как драфты)
↓ немедленно: searchRepository.searchChatsByKeywords → FTS5 MATCH
↓ keywordResults
↓ параллельно (дебаунс 400мс): embedding-клиент → вектор запроса
↓ searchRepository.getChatEmbeddings → cosine similarity ≥ 0.75
↓ embeddingResults → merge (dedupe) → mergedResults
↓ FlatList в сайдбаре: названия + подсветка
```

Будущее (после появления отправки сообщений и API) — уже подготовлено:

```
Отправка сообщения → INSERT в messages + аппенд текста в chats.context
↓ триггер chats_au обновляет chats_fts → keyword-поиск по context работает
↓ генерация title_embedding / context_embedding через embedding-клиент
   (ключ и модель — из подключенного шаблона) → embedding-поиск работает
```

## 5. Что сознательно НЕ делаем в этой итерации

- Никаких реальных API-вызовов, ввода ключей и выбора embedding-модели —
  обёртка готова, подключение отдельной итерацией.
- Никакой записи в `context` — отправка сообщений еще не реализована.
- Никаких сниппетов из context в результатах — только названия + подсветка.
- Никакой группировки по датам в результатах поиска — плоский список.
- Никакой документации — она будет написана после рефакторинга.

## 6. Правила исполнения

- **FSD строго**: UI-обвязка — в `src/app/(tabs)/chat/components/...`,
  логика фичи — в `src/features/chats`, переиспользуемое — в `src/shared`,
  доступ к данным — в `src/lib/db`, типы данных — в `src/types`.
- **Типизация — в файлах типов**: `*.types.ts` рядом с модулем или
  `src/types/*.ts`; в файлах логики — только импорты типов.
- Стиль, именование, структура файлов — по существующим паттернам (§0);
  комментарии — только для неочевидных «почему», в стиле существующего кода.
