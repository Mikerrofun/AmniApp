# План: Поиск чатов (FTS5 по ключевым словам + embedding-задел)

> План для агента-исполнителя. Ветка: `ChatsSearchFeature` (от `main`).
> Цель: рабочий поиск чатов по названию (и по контексту — как только появится
> отправка сообщений), плюс готовая инфраструктура embedding-поиска.
> Embedding-модель выбрана заранее: `nvidia/nemotron-3-embed-1b:free`
> (OpenRouter, OpenAI-совместимый `/embeddings`), API-ключ читается из env
> конфига. Векторное расширение SQLite — `sqlite-vec`.

## 1. Что делаем (сводка)

1. **Миграция v3**: в `chats` добавляются колонки `context` (денормализованный
   текст всех сообщений чата), `title_embedding`, `context_embedding`
   (эмбединги, пока NULL). Создается FTS5-таблица `chats_fts` (title + context)
   с триггерами синхронизации. Подключается расширение `sqlite-vec` и создается
   векторная таблица для KNN-поиска по эмбедингам.
2. **Embedding-обёртка** в `src/lib/ai/embeddings/`: OpenAI-совместимый клиент
   `/embeddings` под OpenRouter. Модель зафиксирована:
   `nvidia/nemotron-3-embed-1b:free`. API-ключ читается из env конфига
   (`EXPO_PUBLIC_OPENROUTER_API_KEY` через `process.env`). Клиент готов к
   вызовам, но деградирует тихо, если ключа нет.
3. **Репозиторий поиска**: keyword-поиск через FTS5 (`MATCH`), чтение/запись
   эмбедингов (колонки `chats` + векторная таблица sqlite-vec).
4. **Обновление эмбедингов — событийное, привязано к источникам изменения
   данных**:
   - `title_embedding` — **сразу в этой итерации**: title определяется первым
     запросом юзера при создании чата, а единственное место его изменения —
     rename в контекстном меню. Значит ровно две точки генерации: создание
     чата и rename. После каждой — перегенерация `title_embedding` и запись
     в БД (при отсутствии ключа/ошибке — тихо пропускается, колонка остается
     NULL до следующей попытки).
   - `context_embedding` — **задел на будущее**: после каждого обмена
     «запрос юзера → ответ ИИ» текст пары аппендится в `context`, и
     эмбединг контекста перестраивается. Точка встраивания — будущий флоу
     отправки сообщений (см. §4).
5. **Стор поиска** (zustand, по паттерну `chats-store`): поисковая строка —
   временное состояние в памяти (как драфты), без записи в БД; результаты
   двух этапов поиска и их мерж.
6. **UI в сайдбаре**: при непустом запросе — плоский список найденных чатов
   (без группировки по датам) с подсветкой совпадений в названии; при пустом —
   обычный сгруппированный список как сейчас.

**Что работает сразу после реализации:** поиск по названию чата (keyword) +
генерация/обновление `title_embedding` при создании и rename (как только в env
появится ключ). **Что заработает автоматически позже:** keyword-поиск по
`context` (колонка заполнится, когда появится отправка сообщений) и
embedding-поиск по `context_embedding` (после встраивания перегенерации во
флоу отправки сообщений).

## 2. Принятые архитектурные решения

1. **Context — денормализованная колонка** в `chats`, а не сборка из `messages`
   на лету. При добавлении каждого сообщения (в будущем) текст аппендится в
   `context`. Поиск читает одну колонку — быстро и просто. Дублирование с
   `messages` осознанное: `messages` — источник истины для отображения истории,
   `context` — поисковый индекс.
2. **Keyword-поиск — SQLite FTS5** (доступен в expo-sqlite). Виртуальная
   таблица + триггеры — синхронизация индекса автоматическая, без ручных
   вызовов из репозитория.
3. **Два независимых дебаунса**: keyword-поиск выполняется мгновенно на каждый
   ввод (локальный FTS, дешево); embedding-поиск — с дебаунсом ~400мс после
   остановки печати + отмена устаревших запросов (AbortController). Это экономит
   API-вызовы, когда они появятся.
4. **Similarity threshold = 0.75** (cosine similarity), константой в конфиге
   embedding-слоя.
5. **Векторное расширение — `sqlite-vec`**: официальная поддержка в
   expo-sqlite (конфиг-плагин `withSQLiteVecExtension` в app.json + загрузка
   расширения при открытии БД). Векторы хранятся в виртуальной таблице
   `vec0`, поиск — `vec_distance_cosine` (KNN), что избавляет от ручного
   перебора векторов в JS. Размерность вектора — константой в конфиге
   embedding-слоя (уточнить фактическую размерность
   `nvidia/nemotron-3-embed-1b:free` при первом реальном вызове; таблица
   `vec0` создается в миграции v3 с этой константой).
6. **Результаты — плоский список** без группировки по датам; показываем
   название с подсветкой совпадений. Сниппеты из context — позже, не в этой
   итерации.
7. **Мерж результатов**: dedupe по id чата; чат, найденный обоими этапами,
   остается одним элементом (приоритет у keyword-результата для подсветки).
8. **API-ключ — из env конфига**: `EXPO_PUBLIC_OPENROUTER_API_KEY`
   (префикс `EXPO_PUBLIC_` — стандарт Expo для доступных в рантайме
   переменных). Отсутствие ключа — не ошибка: embedding-этап тихо
   пропускается, keyword-поиск продолжает работать.

## 3. Задачи

> Во всех задачах: типизация — **только в файлах типов** (`src/types/*.ts`
> или `*.types.ts` рядом с модулем), не внутри файлов с логикой. Структура —
> **строго FSD** (`src/app` → `src/features` → `src/shared` → `src/lib`).
> Если что-то непонятно — смотреть существующие паттерны (список в §0)
> и подгонять под один стиль с ними. Код в плане не приводится — только
> флоу и ссылки на файлы.

### Задача 1. Миграция v3: колонки + FTS5 + sqlite-vec

Файлы: `src/lib/db/db.config.ts`, `src/lib/db/migrations.ts`,
`src/types/chat.ts`, `app.json`.

Флоу:

1. Включить расширение `sqlite-vec` в `app.json` через конфиг-плагин
   expo-sqlite (`withSQLiteVecExtension`) и загрузить его при открытии БД
   (`db.loadExtension(...)` — свериться с актуальными доками expo-sqlite по
   точному имени API и плагина). Без загрузки расширения векторные таблицы
   не создадутся — загрузка должна предшествовать миграции.
2. Поднять `DB_SCHEMA_VERSION` до 3 в `db.config.ts`.
3. В `migrations.ts` добавить блок `if (current < 3)` по образцу v2:
   - `ALTER TABLE chats ADD COLUMN context TEXT NOT NULL DEFAULT ''`;
   - `ALTER TABLE chats ADD COLUMN title_embedding TEXT` (NULL = эмбединг
     еще не сгенерирован);
   - `ALTER TABLE chats ADD COLUMN context_embedding TEXT` (NULL — задел
     на будущее);
   - создать виртуальную таблицу `chats_fts` через
     `CREATE VIRTUAL TABLE ... USING fts5(chat_id UNINDEXED, title, context,
     content='chats', content_rowid=...)` — external-content вариант, чтобы
     не дублировать текст. Внимание: у `chats` нет rowid-совместимого
     INTEGER PRIMARY KEY, поэтому если external-content не ложится cleanly —
     допустим вариант обычной FTS5-таблицы, где `chat_id` хранится UNINDEXED-
     колонкой, а триггеры поддерживают её актуальность. Решение принимает
     исполнитель по факту проверки на устройстве.
   - триггеры синхронизации: `chats_ai` (AFTER INSERT), `chats_ad`
     (AFTER DELETE), `chats_au` (AFTER UPDATE OF title, context) — вставка/
     удаление/обновление строки FTS-индекса при изменении `chats`.
   - создать векторную таблицу sqlite-vec:
     `CREATE VIRTUAL TABLE chats_vec USING vec0(chat_id TEXT PRIMARY KEY,
     title_embedding float[DIM], context_embedding float[DIM])`, где DIM —
     константа размерности из конфига embedding-слоя (см. задачу 3).
     Синхронизация `chats_vec` — из кода репозитория (vec0 не поддерживает
     триггеры): при записи эмбединга репозиторий делает upsert строки,
     при удалении чата — delete. В миграции таблица создается пустой.
   - для существующих БД после создания триггеров выполнить первичное
     наполнение FTS-индекса из текущих строк `chats` (INSERT INTO chats_fts
     SELECT ...). Идемпотентность: блок выполняется один раз по
     `user_version`, свежие БД проходят v1→v3 подряд — проверить, что
     порядок шагов корректен в обоих сценариях (как это сделано в v2).
4. Типы в `src/types/chat.ts`:
   - `ChatRow` дополнить полями `context`, `title_embedding`,
     `context_embedding` (snake_case, как в SQLite);
   - `ChatRecord` **не расширять** — UI-представление чата остается легким,
     context/эмбединги нужны только поисковому слою. Если поисковым функциям
     удобен отдельный рекорд — завести отдельный тип (например,
     `ChatSearchRow` / `ChatEmbeddingRecord`) в этом же файле типов.

### Задача 2. Репозиторий: поддержка новых колонок + поисковые функции

Файлы: `src/lib/db/chats-repository.ts`, новый `src/lib/db/search-repository.ts`,
`src/lib/db/index.ts`.

Флоу:

1. В `chats-repository.ts`: `createChat` при INSERT пишет `context: ''`
   (эмбединги — NULL, не указываем). `renameChat` остается без изменений —
   FTS-триггер подхватит обновление title сам. `mapRow` не трогаем (см. §3.1 —
   `ChatRecord` не расширяется).
2. Новый `search-repository.ts` (или функции внутри `chats-repository.ts`,
   если файл остается компактным — решить по образцу существующего размера):
   - `searchChatsByKeywords(query)` — SELECT из `chats`, JOIN с `chats_fts`
     по `MATCH`; запрос формируется из пользовательской строки безопасно
     (экранирование FTS-синтаксиса — кавычки, спецсимволы; параметризованный
     запрос). Возвращает: id чата, title, флаги/диапазоны совпадений в title
     (для подсветки — через FTS5-функцию `offsets()` или `highlight()`),
     релевантность (bm25). Сортировка: сначала совпадения в title, затем по
     релевантности. Поиск по `context` выполняется тем же запросом — сейчас
     колонка пустая и просто не даст совпадений, позже заработает сама.
   - `searchChatsByEmbedding(vector, kind)` — KNN-запрос к `chats_vec` через
     `MATCH`/`vec_distance_cosine` (sqlite-vec): ближайшие чаты по
     `title_embedding` или `context_embedding` (kind — какой вектор
     сравнивать), с фильтром по threshold 0.75 уже на уровне SQL
     (`WHERE distance <= 1 - threshold` для cosine distance). Возвращает
     id чата + similarity. Если векторная таблица пуста — пустой результат
     (корректное поведение до появления эмбедингов).
   - `updateChatEmbedding(chatId, kind, vector)` — запись вектора: UPDATE
     колонки в `chats` (сериализация в текст/BLOB) + upsert строки в
     `chats_vec`. Вызывается из флоу генерации эмбедингов (задача 6).
   - `deleteChat` (существующий) — убедиться, что строка из `chats_vec`
     тоже удаляется (в том же месте, где удаляется чат).
3. Реэкспортировать новые функции в `src/lib/db/index.ts` (по образцу
   существующих).

### Задача 3. Embedding-обёртка (модель и ключ зафиксированы)

Файлы: новый каталог `src/lib/ai/embeddings/` (структура по образцу
`src/shared/components/ui/ScrollIndicator/`: код, конфиг, типы, index).

Флоу:

1. Типы (`embeddings.types.ts`): интерфейс embedding-клиента
   (`embed(texts: string[], signal?: AbortSignal): Promise<number[][]>`),
   конфиг клиента (baseUrl, apiKey, model), тип вектора.
2. Конфиг (`embeddings.config.ts`): константы —
   `EMBEDDING_MODEL = 'nvidia/nemotron-3-embed-1b:free'`,
   `EMBEDDING_DIMENSIONS` (размерность вектора модели — уточнить при первом
   реальном вызове, используется миграцией для `chats_vec`),
   `SIMILARITY_THRESHOLD = 0.75`, base URL OpenRouter
   (`https://openrouter.ai/api/v1` — согласуется с `src/lib/ai/providers.ts`),
   имя env-переменной `EXPO_PUBLIC_OPENROUTER_API_KEY`.
3. Ключ из env: клиент читает `process.env.EXPO_PUBLIC_OPENROUTER_API_KEY`
   (стандарт Expo для рантайм-доступных переменных; переменную добавить в
   `.env` / env конфиг проекта). Отсутствие ключа — не ошибка: клиент
   возвращает «недоступен» (null/флаг), вызывающий код тихо пропускает
   embedding-этап.
4. Клиент (`embeddings-client.ts`): реализация OpenAI-совместимого
   `POST /embeddings` (headers: Authorization Bearer; body: model, input;
   разбор `data[].embedding`). Чистая функция поверх `fetch`, поддержка
   AbortSignal для отмены. Без side-effects.
5. Утилита cosine similarity — в `src/features/chats/lib/` (рядом с
   `group-chats-by-day.ts`, по его паттерну: чистая функция + при необходимости
   конфиг-файл). Нормализация векторов внутри функции. (Резерв на случай
   сравнения в JS; основной путь — KNN в sqlite-vec, задача 2.)
6. Слой готов к вызовам: его используют стор поиска (задача 4) и флоу
   генерации `title_embedding` (задача 6). Пока ключа нет в env — все
   embedding-вызовы тихо пропускаются, keyword-поиск не зависит от них.

### Задача 4. Стор поиска + хук с дебаунсами

Файлы: `src/features/chats/model/search-store.ts`, `search-store.types.ts`,
`use-chat-search.ts`, реэкспорт в `src/features/chats/index.ts`.

Флоу:

1. Типы в `search-store.types.ts`: состояние поиска (query, результаты
   keyword/embedding/merged, флаг поиска, ошибка), тип результата
   (id чата, title, источник совпадения, диапазоны для подсветки, score).
   Тип результата — общий для двух этапов.
2. `search-store.ts` по паттерну `chats-store.ts` (чистые экшены, работа с
   репозиторием, никаких таймеров внутри стора):
   - состояние: `query`, `keywordResults`, `embeddingResults`, `isSearching`;
   - `searchByKeywords(query)` — синхронно зовет репозиторий (FTS — быстрый
     локальный запрос) и пишет `keywordResults`;
   - `searchByEmbeddings(query, signal)` — асинхронно: получить вектор
     запроса через embedding-клиент (задача 3), затем KNN-поиск по
     `chats_vec` через репозиторий (задача 2: `searchChatsByEmbedding` —
     сравнение и с `title_embedding`, и с `context_embedding`), записать
     `embeddingResults`. Обертка в try/catch: ошибка сети/отсутствие ключа —
     тихо очищает embedding-результаты, не ломая keyword-поиск;
   - `clearSearch()` — сброс всего состояния поиска;
   - мерж двух списков — отдельная чистая функция в `src/features/chats/lib/`
     (dedupe по id, объединение источников совпадения, сортировка).
3. `use-chat-search.ts` — единственная точка входа UI (по образцу
   `use-chat-draft.ts`):
   - `onChangeText` → запись query в стор → **немедленный** keyword-поиск;
   - параллельно таймер-дебаунс ~400мс: по истечении — embedding-поиск;
     каждый новый ввод сбрасывает таймер и **прерывает** предыдущий
     embedding-запрос через AbortController (signal прокидывается в клиент);
   - пустая строка → `clearSearch()` + отмена таймера/запроса;
   - возвращает: query, merged-результаты, флаг активности поиска.
4. Реэкспорты в `src/features/chats/index.ts`.

     существующих `FadeIn`/`LinearTransition`.
3. Подсветка совпадений в названии: диапазоны совпадений приходят из
   keyword-результата (FTS offsets). Реализация — утилита, разбивающая title
   на сегменты (совпало/не совпало), и рендер сегментов с акцентным стилем
   для совпавших. Если для embedding-only совпадений диапазонов нет —
   название рендерится без подсветки.
4. Пустой результат при непустом запросе → заглушка «Ничего не найдено»
   (по образцу существующего `ListEmptyComponent`).
5. Выбор чата из результатов — тот же `handleSelectChat` (setActiveChat +
   закрытие панели на мобиле). Дополнительно: при выборе чата поиск
   сбрасывается (clearSearch), чтобы при следующем открытии сайдбара
   показывался обычный список.
6. i18n: новые ключи в `en.json`/`ru.json` в секции `chats`
   (минимум: «ничего не найдено»). Формулировки — в стиле существующих.

### Задача 6. Генерация title_embedding: создание чата + rename

Файлы: `src/features/chats/model/use-create-chat.ts`,
`src/features/chats/model/use-chat-actions.ts` (rename-флоу),
`src/lib/ai/embeddings/` (задача 3), `search-repository` (задача 2).

Флоу (событийная модель — эмбединг перестраивается ровно в точках изменения
title):

1. **Создание чата**: после успешного `createChat` (title определен по
   первому запросу юзера) — асинхронно, не блокируя UI: вызвать
   embedding-клиент с title → `updateChatEmbedding(chatId, 'title', vector)`.
2. **Rename** (контекстное меню чата — единственное место изменения title):
   после успешного `renameChat` — та же последовательность: клиент →
   `updateChatEmbedding(chatId, 'title', vector)`.
3. Деградация: если ключа нет в env или запрос упал — тихо пропустить
   (title_embedding остается NULL/старым), keyword-поиск не затрагивается.
   Повторная попытка произойдет при следующем rename/создании.
4. Генерация — fire-and-forget с отменой: если чат удалили, пока запрос
   в полете, — не писать результат (проверка существования перед записью
   или молчаливый провал upsert).
5. `context_embedding` здесь НЕ трогаем — его перегенерация встраивается
   в будущий флоу отправки сообщений (см. §4).

### Задача 7. Проверка флоу (ручная, по чек-листу)

1. Создать несколько чатов с разными названиями → поиск по подстроке названия
   находит, подсветка корректна, регистр не важен.
2. Спецсимволы в запросе (`"`, `*`, скобки) не ломают FTS-запрос.
3. Пустой запрос → обычный сгруппированный список.
4. Запрос без совпадений → заглушка.
5. Быстрый набор текста: keyword-результаты обновляются на каждый символ;
   embedding-запрос не уходит чаще, чем раз в ~400мс простоя; при
   переключении чата/закрытии сайдбара поиск сброшен.
6. Rename чата: при наличии ключа в env — `title_embedding` обновляется
   (проверить строку в `chats` и `chats_vec`); без ключа — тихо пропускается,
   ошибок в UI нет.
7. Миграция: БД со старой версией (v2) поднимается на v3 без потери данных;
   свежая установка создает схему сразу v3 (включая `chats_vec`).

## 4. Потоки данных (итоговые)

Ввод поискового запроса:

```
Печать в TextInput (ChatSidebar)
↓ onChangeText → useChatSearch
↓ query → search-store (память, без БД — как драфты)
↓ немедленно: searchRepository.searchChatsByKeywords → FTS5 MATCH
↓ keywordResults
↓ параллельно (дебаунс 400мс): embedding-клиент → вектор запроса
↓ searchRepository.searchChatsByEmbedding → KNN по chats_vec (sqlite-vec),
  cosine distance ≤ 1 − 0.75, против title_embedding и context_embedding
↓ embeddingResults → merge (dedupe) → mergedResults
↓ FlatList в сайдбаре: названия + подсветка
```

Обновление эмбедингов (событийная модель):

```
Сейчас:  создание чата / rename → embedding-клиент (title)
         → updateChatEmbedding → chats.title_embedding + chats_vec
Будущее: обмен «запрос юзера → ответ ИИ»
         → аппенд текста пары в chats.context
         → триггер chats_au обновляет chats_fts → keyword-поиск по context
         → embedding-клиент (context) → updateChatEmbedding
           → chats.context_embedding + chats_vec → embedding-поиск по context
```

## 5. Что сознательно НЕ делаем в этой итерации

- Никакого UI для ввода ключей и смены модели — модель зафиксирована в
  конфиге (`nvidia/nemotron-3-embed-1b:free`), ключ берется из env; смена
  модели позже — одной строкой в `embeddings.config.ts`.
- Никакой записи в `context` и генерации `context_embedding` — отправка
  сообщений еще не реализована (точка встраивания описана в §4).
- Никаких сниппетов из context в результатах — только названия + подсветка.
- Никакой группировки по датам в результатах поиска — плоский список.
- Никакой документации — она будет написана после рефакторинга.

## 6. Правила исполнения

- **FSD строго**: UI-обвязка — в `src/app/(tabs)/chat/components/...`,
  логика фичи — в `src/features/chats`, переиспользуемое — в `src/shared`,
  доступ к данным — в `src/lib/db`, типы данных — в `src/types`.
- **Типизация — в файлах типов**: `*.types.ts` рядом с модулем или
  `src/types/*.ts`; в файлах логики — только импорты типов.
- Стиль, именование, структура файлов — по существующим паттернам (§0);
  комментарии — только для неочевидных «почему», в стиле существующего кода.
