# Общий withRetry для сетевых запросов

---

**Дата:** 19.11.2026
**Теги:** #features #networking #retry #resilience

---

## 1. Зачем

Приложение ходит в сеть напрямую с устройства (Privacy First / BYOK, без
бекенда), а мобильные сети рвутся регулярно: смена Wi-Fi на LTE, спящий
режим, капризный DNS, 502 на шлюзе провайдера. До этой фичи любой такой
микросбой превращался в ошибку для пользователя — при том, что почти все
запросы проекта либо идемпотентны, либо безопасны для повтора до первого
токена. Ретраить «в каждом caller» — значит размазать одну политику
по сторам и хукам; вместо этого ретрай живет внутри сетевых клиентов,
и ни один caller не знает о нем.

## 2. Зафиксированные решения

- **Один общий `withRetry`**, а не пер-вызовные обертки. Ретраятся только
  сеть (fetch reject / `TypeError`), таймаут попытки, HTTP 408/429 и 5xx.
  Любой другой 4xx (400/401/403/404/422…) — наверх сразу, без ретрая.
- **2 попытки** (1 ретрай), фиксированный backoff 400 мс — без экспоненты
  и джиттера: закрываем микросбои, а не штормы.
- **Внешний `AbortSignal` никогда не ретраится.** Отмена юзером или
  размонтирование — не сбой. Таймаут-аборт внутри попытки — ретраится,
  внешний abort — нет.
- **Ретрай внутри клиентов**, а не в вызывающих сторах/хуках.
- **Чат-стрим ретраится только до первого токена**: если `onText` уже
  вызывался, тихий повтор продублировал бы текст. До первой дельты
  ретраятся сеть/таймаут/5xx/429 на начальном fetch — POST
  /chat/completions серверной стороны не мутирует.
- **Локальный SQLite (`src/lib/db`) — не сеть**, вне скоупа.

## 3. Реализация

### 3.1 Модуль src/shared/lib/net/

Общий слой без домена, рядом с `input/` и `search/`:

```
src/shared/lib/net/
├── with-retry.types.ts    # WithRetryOptions, RetryableError
├── with-retry.config.ts   # RETRY_ATTEMPTS = 2, RETRY_BACKOFF_MS = 400
├── with-retry.ts          # withRetry, isRetryableStatus, isRetryableError
└── index.ts               # бочка для внешних импортов
```

```ts
// src/shared/lib/net/with-retry.ts

/**
 * withRetry(fn, opts?) — вызывает fn(attempt); при ретраебельной ошибке
 * и неисчерпанных попытках ждет backoffMs и повторяет, иначе бросает
 * последнюю ошибку. Внешний signal aborted — бросает немедленно, без
 * ретрая и без backoff: проверяется перед первой попыткой, в catch
 * после ошибки и внутри sleep (abort во время сна просыпает промис).
 */
export async function withRetry<T>(
  fn: (attempt: number) => Promise<T>,
  options?: WithRetryOptions,
): Promise<T>

/** 408, 429, 500–599 */
export function isRetryableStatus(status: number): boolean

/**
 * Дефолтный фильтр: TypeError (сеть), AbortError (таймаут попытки —
 * внешний abort проверяется в withRetry отдельно) и статусы
 * isRetryableStatus. Ошибки с числовым полем status (ChatCompletionError,
 * RetryableError) классифицируются по нему.
 */
export function isRetryableError(error: unknown): boolean
```

`RetryableError` — ошибка HTTP-ответа, классифицируемая по статусу:
несет `status?: number`, ретраится только если статус попадает под
`isRetryableStatus` (400 в ней — такой же fail-fast, как у любой 4xx).

Кастомный `shouldRetry` в опциях позволяет сузить фильтр — этим
пользуется только чат-клиент.

### 3.2 models-fetcher: ретрай GET и probe

`fetchAvailableModels`, `fetchProviderJson` (а с ним anthropic/gemini/
cohere) и `probeChatCompletions` обернуты в `withRetry`. Три новых
хелпера вместо дублированного таймаут-кода:

```ts
// src/shared/lib/ai/models-fetcher/fetchers/models-fetcher.ts

/**
 * fetchWithTimeout(url, init, signal?) — одна попытка: внутренний
 * AbortController абортится по таймауту ИЛИ по внешнему signal.
 * Контроллер создается на каждую попытку: таймаут одной попытки
 * ретраится, внешний abort — нет. Ошибки пробрасываются наверх.
 */
async function fetchWithTimeout(url, init, signal?)

/** 5xx/429/408 — бросает RetryableError, чтобы withRetry сделал ретрай */
function throwIfRetryableStatus(status: number): void

/** Классификация ошибки попытки в FetchModelsResult — как раньше */
function classifyFetchError(error, signal?): { ok: false; reason }
```

Классификация не изменилась и осталась снаружи обертки: 401/403 →
`unauthorized` (4xx — fail-fast), `TypeError` без аборта → `network`,
остальное → `other`. Парсинг ответа — тоже снаружи, повторно не ретраится.
Сторы и хуки (`models-store.ensureModels`, `use-base-url-validation`)
не тронуты: in-flight контроллеры и debounce работают как раньше,
ретрай завершается до возврата результата.

### 3.3 Embeddings: ретрай идемпотентного POST

`fetch` внутри `embed` обернут в `withRetry` с внешним signal. POST
/embeddings — чистая функция, повтор безопасен. 4xx (невалидный ключ)
бросается как `RetryableError` со статусом и проваливается наверх сразу.
Callers (`update-context-embedding.ts`, `update-title-embedding.ts`,
`search-store.ts`) не менялись: fire-and-forget тихо деградирует как
раньше, keyword-поиск от эмбедингов не зависит.

### 3.4 Чат: ретрай только до первого токена

```ts
// src/lib/ai/openai-compat-client.ts

let emitted = false;
const handleText = (text: string) => {
  emitted = true;
  onText(text);
};

const { reader, firstChunk } = await withRetry(
  async () => {
    // fetch + ok-проверка + первое чтение из стрима
    ...
  },
  {
    signal,
    shouldRetry: (error) => !emitted && isRetryableError(error),
  },
);
```

В ретраебельный шаг входит начальный fetch, проверка `response.ok` и
первое чтение из стрима — до первой дельты повтор безопасен. Ошибка
посреди стрима (со второго чтения) — наверх без ретрая, `partialText`
сохраняется как раньше. `ChatCompletionError` с 4xx — fail-fast, честная
ошибка юзеру без 400 мс задержки. Внешний abort (юзер ушел из чата) —
без ретрая. Контракт `streamChatCompletion` не изменился —
`use-chat-actions.ts` не тронут.

## 4. Поток данных

```
Вызов клиента (fetchAvailableModels / embed / streamChatCompletion)
  ↓
withRetry(попытка, { signal })
  ├── signal aborted → бросить немедленно
  ├── попытка: fetchWithTimeout / fetch
  │     ├── успех → результат наверх
  │     ├── TypeError / таймаут-аборт / 408 / 429 / 5xx → ретраебельно
  │     └── другой 4xx / внешний abort → наверх сразу
  └── ретраебельно и attempt < 2 → sleep 400 мс → следующая попытка
        └── abort во время сна → бросить, второй попытки нет
```

## 5. Почему так, а не иначе

1. **Ретрай в клиентах, а не в caller'ах.** У ретрая одна политика
   (что ретраить, сколько, какая пауза) — держать ее в одном месте
   дешевле, чем повторять в каждом сторе. Плюс fire-and-forget либы
   (эмбединги заголовков) вообще некому ретраить снаружи.
2. **Фиксированный backoff без экспоненты и джиттера.** Ровно один
   ретрай через 400 мс закрывает микросбой сети; экспонента и
   `Retry-After` нужны при повторных штормах, которых здесь не бывает —
   запросы идут по действию пользователя, а не по расписанию.
3. **Внешний abort — не ошибка.** Отмена — нормальный путь (юзер закрыл
   чат, сменил ключ), повторять за ней нечего. Поэтому abort проверяется
   отдельно от фильтра ошибок: и до попытки, и в catch, и во время сна.
4. **Таймаут — на попытку, а не на весь вызов.** Каждый запрос получает
   свои N мс; иначе один ретрай съедал бы таймаут первого.
5. **Чат ретраится только до первой дельты.** Стрим уже отдал текст —
   повтор с нуля продублировал бы его в UI. До первой дельты повтор
   безопасен: POST /chat/completions не мутирует серверное состояние.
6. **Классификация ошибок models-fetcher не тронута.** Фетчеры возвращают
   `FetchModelsResult`, а не бросают — `withRetry` обернут вокруг сырого
   fetch, а разбор ответа остался снаружи обертки.

## 6. Текущие ограничения

- **Ретраебельные статусы бросаются внутри попытки** (`RetryableError`
  со статусом), а 4xx обрабатываются возвратом результата — снаружи
  обертки это неотличимо от прежнего поведения, но внутри попытки
  ошибка и ответ существуют в двух формах.
- **Ошибки со второго чтения чат-стрима не ретраятся**, даже если дельт
  еще не было (пустой первый чанк) — ретраебельный шаг заканчивается
  первым чтением.
- **`Retry-After` из 429 не учитывается** — фиксированные 400 мс.
- **Мутаций с idempotency key в проекте нет**; если появятся, ключ +
  ретрай добавлять отдельной задачей по этому же образцу.
- **Специализированных тестов на withRetry нет** — проверка типами
  (`tsc --noEmit`) и существующими тестами проекта.

## Преимущества

- ✅ Одна политика ретрая для всей сети проекта: 2 попытки, 400 мс, только сеть/таймаут/408/429/5xx
- ✅ Fail-fast на честных 4xx: невалидный ключ виден юзеру сразу, без задержки ретрая
- ✅ Внешняя отмена никогда не дублируется: abort — мгновенный выход на любом этапе
- ✅ Чат не дублирует текст: стрим ретраится только до первого токена
- ✅ Ни один caller (сторы, хуки, fire-and-forget) не изменился
- ✅ Классификация ошибок и парсинг остались снаружи обертки — поведение клиентов не изменилось
